# R setup for ChatGPT Work containers

In this interactive Ubuntu 24.04 Work execution sandbox, `cat /proc/self/uid_map /proc/self/gid_map` prints `0 0 1` twice and `runuser -u _apt -- id` fails with `cannot set groups: Operation not permitted`. This is not a claim about every Work or Codex runner: the PR reviewer reports full maps and a working `_apt` user in its own environment. Gate the per-command `APT::Sandbox::User=root` override on the observed single-ID map, not the product name.

Add a separate `tools/setup-work-container-r.sh` and document its invocation in CONTRIBUTING.md. Keep the Claude script unchanged. Download signed Ubuntu packages with private apt state/cache and extract their payloads into a private prefix, without invoking dpkg maintainer scripts or modifying system packages. Relocate R's Debian wrapper and configuration symlinks, and write an activation file for R/Rscript, libraries and workers. Keep TLS and package signature verification and existing network policy. Install the real yesno package from its CRAN GitHub mirror at a pinned commit, then install rcicr. Make reruns safe.

The private installation was tested manually: R 4.3.3, testthat 3.2.1, real yesno 0.1.3 and rcicr load, two PSOCK workers load rcicr, and testthat::test_local() finishes without failures and with one root-permission skip. Set _R_CHECK_LIMIT_CORES_=true for tests because detectCores() sees host CPUs. Validate the actual script with an initial installation and a rerun; the riskiest step is relocation of the Debian R paths, especially worker startup. This is a testing environment, not a complete CRAN release toolchain. Package R code, numerical output, CI workflows, and release gates are outside this PR.
